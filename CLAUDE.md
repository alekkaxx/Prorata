# prorata

Биллинг-движок подписок: события → инвойс с объяснением каждой строки.
Библиотека, чистые функции. НЕТ: HTTP, БД, CLI, конкурентности, LLM в рантайме.
Витрина AI-конвейера: этот файл маршрутизирует РАЗРАБОТКУ по моделям. Контекст проекта — PLAN.md.

## Команды

```bash
make check                      # build + vet + test — единственное условие перед коммитом
go test -run TestGolden ./...   # только golden-сценарии (эталонные инвойсы)
go test -run TestGrace ./...    # тесты одного правила: TestCharge, TestGrace, TestIntervalSwitch
go test -run Property ./...     # property на pgregory.net/rapid
go test -run 'Never|Bounded' ./...  # инвариантные property: кредит ≤ уплаченного, баланс не уходит в минус
```

Флага `-update` для golden нет и не будет: эталон выводится из спеки руками, а не снимается
с реализации. Golden, записанный с кода, проверяет только то, что код равен сам себе.

## Старт сессии

Прочитай PLAN.md целиком и спеку текущей задачи (specs/NN-*.md). Весь репо подряд не читать;
разведку по коду делать узким сабагентом, в основной контекст брать только вывод.

## Роутинг задач по моделям

| Задача | Агент | Гейт |
|---|---|---|
| дизайн ядра/API, округления, упавшие property | architect (opus) | ревью человека |
| правило по спеке + тесты | builder (sonnet) | golden + property + architect |
| фикстуры, табличные тесты, механика, доки | mechanic (haiku) | make check |

Эскалация: 2 фейла гейта подряд → тир выше. Публичный API или инварианты → только architect.
Обратная эскалация: builder обязан остановиться и вернуть наверх ошибку в спеке (арифметика, дыра), а не подкрутить тест под неё.
Вниз: без спеки в specs/ builder и mechanic не стартуют.

## Инварианты (нарушение = стоп и architect, не «подкрутить тест»)

- Деньги не создаются и не исчезают: сумма allocation == исходной сумме.
- Расчёт идемпотентен: тот же вход → байт-в-байт тот же инвойс.
- Кредит ≤ фактически уплаченного.
- Каждая строка инвойса несёт RuleID и объяснение.

**Ни одно правило ниже не перебивает эти четыре.** Если удобная реализация требует нарушить
инвариант — неверна реализация, а не инвариант. Спор об инварианте решает architect, и только
он: builder и mechanic обязаны остановиться и вернуть вопрос наверх.

## Домен: решения, которые НЕ переоткрывать

Приняты в specs/00-core.md с обоснованием и отвергнутыми альтернативами. Кажущееся
отклонение в цифрах — почти всегда одно из этих правил, а не баг реализации.

- **Округление — half away from zero** (1.5 → 2, −1.5 → −2), симметрично по знаку. Не half-even.
- **Никакого float.** Money = int64 центов; проценты — базисные пункты (`bps`, 10000 = 100%).
- **Дробление суммы — только `Money.Allocate`** (largest remainder). Независимое округление
  частей — классическая ловушка: сумма частей разойдётся с исходной.
- **Период — полуинтервал `[Start, End)`**, гранулярность proration — целые дни. Конец периода
  == старт следующего, ни один день не считается дважды.
- **Календарный месяц с клампом дня**: 31 янв + месяц = 28/29 фев. Год = 12 месяцев. Не «30 дней».
- **События приходят отсортированными.** Движок НЕ сортирует сам — нарушение порядка это ошибка
  вызывающего, молчаливая сортировка замаскировала бы его баг.
- **Строки инвойса рождают только события внутри запрошенного периода.** События до периода
  строят состояние, но в инвойс не попадают.
- **VAT считается по строкам, не от итога** — иначе расхождение на копейку (см. specs/09-vat.md).
- **Базис возврата — фактически уплаченный кэш**, не номинал плана (specs/08-refund.md).
- **Grace не двигает деньги**: нулевые строки-маркеры, кэш прячется в held (specs/10-grace.md).

## Как правило подключается к движку

Правило = файл `rule_*.go`, регистрирующий обработчик своего `EventType` через `registerRule`
в `init()`. Поэтому **builder добавляет правило, не редактируя ядро** — конвенция «ядро только
через architect» обеспечена механически, а не дисциплиной. Если для правила понадобилось
править engine.go — это сигнал остановиться и идти к architect, а не признак сложного правила.

## Конвейер правила

спека (architect) → фикстуры+падающие тесты (mechanic) → реализация (builder)
→ гейт (architect, вердикт в спеку) → строка в README-экономику.
Ритуал: skill add-rule.
Сжатый режим: по решению владельца mechanic-шаг (фикстуры+падающие тесты) может выполнить builder — след в теле коммита.
Уборка после гейтов (simplify/рефакторинг): отдельный `refactor(`-коммит; ядро трогает только
architect; в теле коммита — доказательство «golden байт-в-байт, make check зелёный».

## Коммиты

Префикс = шаг конвейера: `spec(` / `test(` / `feat(` / `gate(`, ядро — `core(`, уборка — `refactor(`, доки — `docs(`.
В теле КАЖДОГО коммита — строка `Tier: <architect|builder|mechanic>` (кто исполнял; сжатый режим помечать тут же).
Сообщения по-русски. `Co-Authored-By: Claude` оставляем — витрина ИИшность не скрывает.

Пример тела:

```
Tier: builder (sonnet)

Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>
```

Правило `Tier:` проверяется механически: хук `.githooks/commit-msg` отклоняет коммит без этой
строки. Включается один раз на клон — `git config core.hooksPath .githooks`. Инструкция в этом
файле остаётся контекстом (её можно забыть — 3 коммита из первых 65 её и забыли), хук работает
независимо от решений модели. Правило, которое обязано выполниться, живёт в хуке, а не в CLAUDE.md.

## Структура

Одно правило = rule_<name>.go + specs/NN-<name>.md + golden/NN-*.json.
Ядро: money.go period.go plan.go event.go invoice.go engine.go — менять только через architect.

## Стиль кода

Все комментарии — godoc, на английском. Русских комментариев в .go-файлах не бывает.

## Без явной просьбы — НЕ делать

Каждый запрет — с тем, что делать вместо.

- **Не создавать файлы вне конвенции** (helpers.go/utils.go запрещены) — общий код правил живёт
  рядом с ядром, а решение о его месте принимает architect.
- **Не менять ядро и публичный API** в задачах уровня builder/mechanic — понадобилось, значит
  задача не того тира: остановиться и вернуть наверх.
- **Не расширять скоуп** (HTTP/БД/CLI/валюты) — витрина, не продукт; идею записать в PLAN.md
  и оставить там.
- **Не читать golden целиком** — только дифф упавшего сценария: файлов десятки, а нужен один.
- **Не гнать `go test` вместо `make check`** перед коммитом — vet ловит то, чего тесты не видят.

## Красные флаги — сигнал, что задача поехала

Если в собственном рассуждении появилось «заодно поправлю», «раз уж я здесь», «до кучи
причешу», «а ещё стоило бы» — это выход за границы задачи, а не полезная инициатива.
Доделай ровно то, что просили, остальное предложи словами и остановись.

Отдельно: **тест, который проходит и с фиксом, и без него, — не тест.** Прежде чем считать
правило готовым, убедись, что его тесты падают на реализации без этого правила. Тест,
подкрученный под неверную спеку, хуже отсутствующего: он создаёт ложную уверенность.

## Проверка

make check = go build + go vet + go test ./... (property на pgregory.net/rapid).
Перед коммитом — зелёный make check, других условий нет.

## Этот файл работает, если

- правило доезжает до гейта с первого захода, а второй заход случается только там, где в спеке
  действительно дыра;
- builder возвращает ошибку спеки наверх, вместо того чтобы подогнать под неё тест;
- ядро не правится в задачах builder/mechanic — и это не требует напоминаний;
- в диффе нет строк, которых никто не просил.

Если что-то из этого перестало выполняться — правило здесь либо расплывчато, либо потерялось
среди лишних. Чинить надо файл, а не повторять инструкцию в чате.
