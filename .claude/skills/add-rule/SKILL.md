# add-rule: конвейер добавления правила биллинга

Взять следующий номер NN (по specs/). Роли исполняются агентами из .claude/agents/ — не смешивать тиры.

## Шаги

1. **architect — спека.** Написать specs/NN-<rule>.md:
   - что делает правило и когда срабатывает;
   - краевые кейсы (границы периодов, 31-е число, февраль, нулевые суммы);
   - 3–5 примеров вход→выход с точными цифрами (центы), точными RuleID и точными строками описаний — mechanic скопирует их буквально;
   - секция `## Gate` — пустая, заполнится на шаге 4.
   Коммит: `spec(NN-<rule>): ...` с `Tier: architect`.

2. **mechanic — фикстуры и падающие тесты.** По спеке: golden/NN-*.json + rule_<name>_test.go (табличные). Значения — только из спеки. Код компилируется, тесты падают.
   Коммит: `test(NN-<rule>): ...` с `Tier: mechanic (haiku)`.

3. **builder — реализация.** rule_<name>.go до зелёного `make check`. Ожидаемые значения тестов не менять; конфликт со спекой → эскалация architect.
   Коммит: `feat(NN-<rule>): ...` с `Tier: builder (sonnet)`.

4. **architect — гейт.** Ревью диффа против спеки и инвариантов CLAUDE.md. Вердикт в спеку: `## Gate: pass|fail — причина`. Fail → назад на шаг 3; два fail подряд → правило реализует architect сам.
   Коммит: `gate(NN-<rule>): pass|fail` с `Tier: architect`.

5. **Экономика.** Строка в README-табличку: правило → тир, которым доехало → число заходов на гейт.

## Эскалация

- 2 проваленных гейта подряд → тир выше.
- Правка ядра/публичного API потребовалась в шаге 2–3 → стоп, задача architect.
- Property-тест упал → разбирает architect.
