# 07-trial — бесплатный триал и конверсия в платный

Тир спеки: architect. Реализация: builder (`rule_trial.go`). Фикстуры/тесты: mechanic.

Ядро для этого правила уже подготовлено architect'ом (коммит
`core(trial): EventTrial/EventConvert + state.trial для правила 07`):

- `EventTrial` (`"trial_start"`) и `EventConvert` (`"trial_convert"`) — два новых
  типа события; поля `Event` не расширялись (обе фазы работают на `At` + `PlanID`);
- `state.trial bool` — явный флаг триала: отличает триал (`paid == 0`, ничего не
  списывали) от подписки на $0-план.

Builder пишет **только** `rule_trial.go` — два обработчика (`EventTrial`,
`EventConvert`), регистрируемых через `registerRule` в `init()`. Ядро не трогать.
Хуки `applyPromo`/`applyCredit` не меняются (см. D6).

## Что делает правило

Триал — бесплатный доступ к плану на его первый биллинг-период с последующим
явным переходом на оплату. Механика разнесена на две фазы (два события).

**Фаза 1 — старт триала (`EventTrial`, обработчик в `rule_trial.go`):**

1. План берётся из каталога по `Event.PlanID`. Неизвестный план → ошибка
   `prorata: trial: unknown plan "<id>"`.
2. Если подписка уже активна (`st.plan != nil`) → ошибка
   `prorata: trial: already subscribed` (триал — только онбординг с чистого
   состояния, см. D5).
3. Триал-период: `[ev.At, AddInterval(ev.At, plan.Interval))` — та же длина и
   тот же кламп дня (D3 ядра), что и у платного периода этого плана (см. D1).
4. Состояние: `plan`, `periodStart`, `periodEnd`, `paid = 0`, `trial = true`.
5. Строка инвойса (одна, **нулевая**):
   - `RuleID`: `trial.start`
   - `Description`: `<plan.ID>: trial <start> to <end> (free)`, даты в UTC формата `2006-01-02`
   - `Amount`: `0`

**Фаза 2 — конверсия (`EventConvert`, обработчик в `rule_trial.go`):**

1. Если триал не активен (`!st.trial`) → ошибка `prorata: convert: no active trial`
   (сюда попадает и пустое состояние, и активная **платная** подписка).
2. План берётся из каталога по `Event.PlanID` (целевой план — тот же триальный или
   другой, см. D8). Неизвестный план → ошибка `prorata: convert: unknown plan "<id>"`.
3. Новый платный период: `[ev.At, AddInterval(ev.At, plan.Interval))`.
4. Состояние: `plan = целевой`, `periodStart = ev.At`, `periodEnd`, `paid = plan.Price`,
   `trial = false`. Остаток триала (был бесплатным, `paid == 0`) **сгорает** — нет
   ни кредита, ни возврата (см. D4).
5. Строка инвойса (одна):
   - `RuleID`: `convert.charge`
   - `Description`: `<plan.ID>: full period <start> to <end>`, даты в UTC формата `2006-01-02`
   - `Amount`: `plan.Price`

Напоминание из ядра: строку в инвойс включает движок только если событие внутри
запрошенного периода; правило строку возвращает всегда. `applyPromo`/`applyCredit`
отрабатывают на строках обеих фаз (см. D6).

## Ключевые решения (решение → почему → отвергнутая альтернатива)

### D1. Модель триала — отдельное событие `EventTrial`, `paid` остаётся 0

**Решение:** триал — самостоятельное событие `EventTrial`, которое открывает
биллинг-период на плане с `state.paid = 0` и `state.trial = true`. Длина триала =
один биллинг-интервал плана (`AddInterval`), нового поля длины нет.

**Почему:** ключевой инвариант — «кредит ≤ фактически уплаченного». Триал должен
хранить `paid = 0`, иначе последующий даунгрейд/апгрейд кредитовал бы деньги,
которых клиент не платил. `EventSubscribe` ставит `paid = plan.Price` — это неверно
для триала; значит триалу нужно **своё** событие, ставящее `paid = 0`. Длину, равную
интервалу плана, даёт уже существующий `AddInterval` — это «первый период бесплатно»,
поведение, которое пользователи знают.

**Отвергнуто:**
- **`subscribe` + промо −100%** (первый заряд скидывается в 0). `subscribe` ставит
  `paid = plan.Price`, а клиент заплатил 0 → прямое нарушение «кредит ≤ уплаченного»
  при следующем изменении плана. Плюс строки `charge.full` + `promo.percent` вместо
  честной «trial»-строки — слабее объяснимость.
- **`subscribe` на фиктивный $0-план из каталога.** Засоряет каталог парным
  $0-планом на каждый триальный план; строка — `charge.full` с суммой 0, без
  RuleID `trial.*`, объяснимость «почему бесплатно» теряется; `paid = 0` неотличим
  от реального $0-плана.
- **Поле `TrialDays` у `Plan` (или `Days` у `Event`).** Расширяет модель ради
  произвольной длины триала, которой витрине не требуется; «первый период бесплатно»
  выражается нулём нового кода.

### D2. Строка триала — нулевая строка `trial.start` с RuleID

**Решение:** фаза 1 возвращает **одну строку** с `Amount = 0`, `RuleID = trial.start`,
непустым `Description`. Не «нет строки».

**Почему:** инвойс обязан объяснять, **почему** период бесплатен, — это и есть
объяснимость из PLAN. Инвариант «каждая строка несёт RuleID» выполнен: строка
несёт RuleID и описание. Движок отвергает строки с пустым `RuleID`/`Description`,
но **не** с нулевым `Amount` (проверка в `engine.go` — только на пустоту RuleID и
Description), поэтому нулевая строка легальна и проходит в инвойс. `Total`
нулевой строки = 0 — деньги не создаются.

**Отвергнуто:** отсутствие строки (фаза 1 возвращает `nil`) — инвойс за
триал-период оказывается пустым и молча, зритель не видит, что доступ был и почему
он бесплатен; теряется след правила в инвойсе.

### D3. Конверсия — отдельное событие `EventConvert`, не reuse subscribe/upgrade

**Решение:** переход «триал → платно» — самостоятельное событие `EventConvert`,
которое списывает целевой план **полностью** за свежий период от `ev.At` и снимает
флаг триала.

**Почему:** ни одно существующее событие не подходит. `EventSubscribe` падает при
`st.plan != nil` («already subscribed») — пришлось бы менять его контракт. `EventUpgrade`
**запрещает тот же план** (`upgrade: already on plan`), а конверсия триала на **тот же**
план — самый частый случай; плюс upgrade выпустил бы шумную нулевую строку
`prorate.credit` (кредит остатка при `paid == 0` = 0). Своё событие даёт чистую
семантику и одну честную строку `convert.charge`.

**Отвергнуто:**
- **Ослабить `subscribe`, чтобы он разрешал старт из триала** — размывает ошибку
  «already subscribed» и трогает правило уровня builder.
- **Конверсия через `EventUpgrade`** — запрещает конверсию на тот же план (главный
  случай) и добавляет нулевую кредитную строку-шум.

### D4. Остаток триала при конверсии сгорает — нечего кредитовать

**Решение:** при конверсии **до** конца триала (в середине) неиспользованный
остаток триала **сгорает**: ни кредита, ни возврата. Списывается полный новый
период от `ev.At`.

**Почему:** триал был бесплатным (`paid = 0`), поэтому денежная стоимость его
остатка — ноль; кредитовать/возвращать нечего, а `Allocate(0, …)` дал бы ровно 0.
Это прямо следствие инварианта «кредит ≤ уплаченного»: заплачено 0 → кредит 0.
Поведение единообразно для конверсии в середине триала, ровно в конце (день-в-день)
и после конца — всегда «полный заряд нового периода от `ev.At`».

**Отвергнуто:** переносить остаток триала как скидку/кредит на первый платный
период — создаёт кредит на непотраченные деньги (`paid == 0`), нарушает инвариант и
экономически бессмыслен («компенсируем неистраченный бесплатный период»).

### D5. Триал требует отсутствия активной подписки

**Решение:** `EventTrial` при `st.plan != nil` → ошибка `trial: already subscribed`.
Триал — только стартовое состояние.

**Почему:** «триал поверх активной подписки» не имеет денежного смысла (клиент уже
платит) и создал бы неоднозначность с `paid`/`creditBalance`. Требование чистого
состояния делает триал детерминированным началом и сразу закрывает взаимодействие
с кредитным балансом (см. D6): на старте триала `creditBalance = 0`.

**Отвергнуто:** разрешать триал поверх подписки с обнулением/сохранением `paid` —
множит краевые случаи (что с оплаченным остатком? с балансом?) ради сценария,
которого в онбординге не бывает.

### D6. Промо и кредитный баланс — без спец-логики (переиспользуют ядро)

**Решение:** правило `rule_trial.go` **не трогает** `applyPromo`/`applyCredit`.
Промо, взведённый до или во время триала, **не сгорает** на нулевой строке триала
(`base = 0`) и применяется к первому реальному заряду — заряду конверсии.
Кредитный баланс в скоупе триала равен 0 (см. D5), взаимодействия нет.

**Почему:** это ровно D3 правила 04 «сгорание только при `base > 0`»: `trial.start`
даёт `base = 0`, `applyPromo` пропускает и **оставляет промо взведённым**. Значит
акция «−20% на первый платёж» переживает бесплатный триал и срабатывает на
конверсии, а не тратится впустую на $0. Никакого нового кода в ядре не нужно —
поведение эмерджентно из уже загейченного хука.

**Отвергнуто:** явно сжигать/сохранять промо в правиле триала — дублирует логику
`applyPromo`, ломает симметрию «скидку применяет только движок».

### D7. Конверсия явная, а не автоматическая по истечении триала

**Решение:** оплата начинается только при пришедшем событии `EventConvert`. Движок
не «дозаряжает» по факту наступления `periodEnd` триала.

**Почему:** модель событийная и детерминированная (D4 ядра) — нет строки без
события; у движка нет таймеров и часов. Триал без события конверсии не порождает
ни одного заряда: инвойс за такой период — пустой (`total 0`). Кто именно решает,
что триал сконвертирован (шедулер вызывающего), — вне библиотеки.

**Отвергнуто:** неявный автозаряд в конце триал-периода — потребовал бы «текущего
времени» внутри `Compute`, разрушив чистоту и идемпотентность.

### D8. Целевой план конверсии — любой известный план, единообразно

**Решение:** `EventConvert` списывает план из `Event.PlanID` — это триальный план
(частый случай) **или** другой план (апселл/даунселл на конверсии). Обработка
единообразна: полный заряд целевого плана за новый период, без кредита.

**Почему:** так как триал бесплатен, остатка для кредита нет **ни при каком**
целевом плане — значит нет причины городить проверку «тот же план». Один код-путь
покрывает и «плачу за то, что триалил», и «на конверсии беру план дороже». Никакой
неоднозначности с upgrade нет: во время триала (`st.trial == true`) применяется
только конверсия.

**Отвергнуто:** запретить конверсию на другой план (только тот же) — добавляет
лишний guard и заставляет делать два события (`convert` + `upgrade`) там, где
хватает одного; при `paid == 0` разница чисто номинальная.

## Краевые кейсы

- **Триал поверх активной подписки** → ошибка `trial: already subscribed` (D5).
- **Конверсия день-в-день с концом триала** (`convert.At == trial.periodEnd`) →
  обычный полный заряд нового периода от `ev.At`; частный случай D4 (пример 1).
- **Конверсия в середине триала** → остаток триала сгорает, полный заряд от `ev.At`,
  кредитной строки нет (пример 3).
- **Конверсия после конца триал-периода** → разрешена; полный заряд от `ev.At`.
  Промежуток между концом триала и конверсией не покрыт и не заряжен (нет события —
  нет строки), что согласуется с D7.
- **Триал без конверсии** → ни одного заряда; инвойс за период после старта триала
  содержит только нулевую `trial.start` (если старт в периоде) либо пуст (`total 0`).
- **Конверсия без активного триала** (пустое состояние или платная подписка) →
  ошибка `convert: no active trial`.
- **Неизвестный план** в любой фазе → соответствующая ошибка `unknown plan`.
- **Промо до/во время триала** → переживает нулевой заряд, применяется на конверсии
  (D6, пример 4).
- **Отмена во время триала** — вне скоупа правила 07. Явная отмена — это будущее
  правило `cancel` (`EventCancel`, бэклог), которого пока нет; сейчас несконвертированный
  триал просто не порождает заряда. Граница скоупа отмечена здесь намеренно.

## Табличные тесты (rule_trial_test.go, пишет mechanic)

Через публичный `Compute` (каталог из примеров):

   (флаг `trial` не взведён);
