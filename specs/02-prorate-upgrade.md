# 02-prorate-upgrade — proration при апгрейде посреди периода

Тир спеки: architect. Реализация: builder (`rule_prorate.go`). Фикстуры/тесты: mechanic.

## Что делает правило

Обрабатывает `EventUpgrade`: смену активной подписки на другой план посреди
текущего биллинг-периода. Правило делает две вещи одной транзакцией:

1. **кредитует неиспользованный остаток** старого плана за оставшиеся дни;
2. **списывает новый план в полном объёме** за его первый биллинг-период от даты апгрейда.

Правило порождает **две строки** (кредит, затем списание) и переписывает
состояние подписки на новый план.

Поведение по шагам:

1. Активная подписка обязательна. Если `st.plan == nil` → ошибка
   `prorata: upgrade: no active subscription`.
2. Новый план берётся из каталога по `ev.PlanID`. Неизвестный →
   `prorata: upgrade: unknown plan "<id>"`.
3. Апгрейд на тот же план запрещён: если `st.plan.ID == ev.PlanID` →
   `prorata: upgrade: already on plan "<id>"`.
4. Считается кредит остатка старого плана (формула — D3 ниже).
5. Считается новый период: `[ev.At, AddInterval(ev.At, newPlan.Interval))` —
   кламп дня по D3 из specs/00-core.md.
6. Состояние переписывается на новый план:
   `plan = newPlan`, `periodStart = ev.At`, `periodEnd = newEnd`,
   `paid = newPlan.Price`.
7. Возвращаются две строки в порядке `[кредит, списание]`.

Напоминание из ядра (engine.go): в инвойс строки включает движок только для
событий внутри запрошенного периода; правило строки возвращает всегда.

## Ключевые решения (решение → почему → отвергнутая альтернатива)

### D1. Кредит — по дням, через `Allocate([used, remaining])`

**Решение:** остаток считается в **днях** (D3 ядра). Пусть
`total = Period{periodStart, periodEnd}.Days()`,
`rem = Period{ev.At, periodEnd}.Days()`, `used = total - rem`.
Кредит = **вторая часть** от `st.paid.Allocate([]int64{used, rem})`, взятая с
минусом. То есть уплаченная за старый период сумма делится методом наибольших
остатков на «использованную» и «оставшуюся» доли, и клиенту возвращается
именно оставшаяся доля.

**Почему:** это напрямую даёт инвариант **кредит ≤ уплаченного**: `Allocate`
дробит ровно `st.paid` на неотрицательные части, сумма которых равна `st.paid`,
поэтому любая одна часть ≤ `st.paid`. Копейка не теряется по построению
(инвариант D2 ядра). Дни — та точность, которую человек проверяет в инвойсе
руками.

**Отвергнуто:** `st.paid.Percent(rem*10000/total)` — независимое округление
процента не гарантирует «часть ≤ целого» на краях и рвёт связь с
allocation-инвариантом; отдельная формула `paid - paid*used/total` с ручным
округлением — повторяет логику `Allocate` хуже и рискует потерять цент.

### D2. Списание нового плана — полное, как charge.full, но своим RuleID

**Решение:** новый план списывается в полном объёме за первый период
`[ev.At, AddInterval(ev.At, newPlan.Interval))`. Строка идентична по форме
строке `charge.full`, но несёт RuleID `prorate.charge` — потому что её породило
правило proration, а не правило подписки.

**Почему:** RuleID идентифицирует **правило-источник** строки (D5 ядра); две
разные строки апгрейда должны трассироваться в `rule_prorate.go`. Полное
списание нового плана (а не пропорциональное) — сознательная модель биллинга:
новый период начинается заново от даты апгрейда, а переплата за старый
возвращается кредитом отдельной строкой. Так итог объясним двумя простыми
строками вместо одной непрозрачной дельты.

**Отвергнуто:** переиспользовать RuleID `charge.full` (смешивает источники,
ломает трассировку правило→строка); пропорционально списывать новый план до
конца старого периода (тогда периоды бьются и якорь ренью плывёт — лишняя
сложность без выгоды для витрины).

### D3. Формула дней и клампы

**Решение:** `total`, `rem`, `used` — целые дни по `Period.Days()` (полные
24h-сутки, полуинтервал). `rem` клампится снизу нулём:
`if rem < 0 { rem = 0 }`. Новый `periodEnd = AddInterval(ev.At, newPlan.Interval)`
клампит день по правилам ядра (31 янв + месяц = 28/29 фев).

**Почему:** `used = total - rem` гарантирует, что веса суммируются ровно в
`total` (валидный вход `Allocate`), а `used ≥ 0`, потому что `ev.At ≥ periodStart`
(события отсортированы, subscribe задаёт `periodStart`). Кламп `rem` снизу
покрывает апгрейд после истечения старого периода: остаток нулевой, кредита нет,
новый план всё равно списывается.

**Отвергнуто:** ошибка при апгрейде за пределами старого периода
(over-strict — поздний апгрейд легитимен, остаток просто равен нулю); считать
`rem` и `used` двумя независимыми вызовами `Period.Days` (на неровных долях
секунд они могут не суммироваться в `total` и сломать инвариант суммы весов).

### D4. Состояние после апгрейда — новый план, `paid = newPlan.Price`

**Решение:** `paid` становится **полной** ценой нового плана, а не «цена минус
кредит». Периодные поля перезаписываются на новый план.

**Почему:** `paid` — база для будущих кредитов (следующего апгрейда/даунгрейда).
Клиент за новый период фактически «оплатил» полную цену нового плана
(строка `prorate.charge`), а кредит — возврат за *старый* период, к новой базе
отношения не имеет. Так инвариант «кредит ≤ уплаченного» остаётся честным при
цепочке апгрейдов.

**Отвергнуто:** `paid = newPlan.Price - credit` (занижает базу и урежет
законный будущий кредит); хранить историю всех оплат (вне скоупа — движку для
proration достаточно оплаты текущего периода).

### D5. Правило механическое, цены не сравнивает

**Решение:** правило не проверяет, дороже новый план старого или дешевле. Выбор
«апгрейд vs даунгрейд» делает вызывающий через `EventType`. Единственный
семантический запрет — апгрейд на тот же план (D-шаг 3).

**Почему:** «дороже» неоднозначно при смене интервала ($20/мес vs $480/год);
экономика даунгрейда (кредит на будущий баланс, не возврат) — отдельное
правило №4. Связывать proration с порядком цен = хрупкость без пользы.

**Отвергнуто:** требовать `newPrice ≥ oldPrice` (ломается на смене интервала и
дублирует ответственность правила даунгрейда).

## RuleID и формат строк

| строка | RuleID | Description | Amount |
|---|---|---|---|
| кредит остатка | `prorate.credit` | `<oldPlan.ID>: unused <rem>/<total> days <ev.At> to <old periodEnd>` | `-credit` (≤ 0) |
| списание нового | `prorate.charge` | `<newPlan.ID>: full period <ev.At> to <newEnd>` | `+newPlan.Price` |

Даты — UTC формата `2006-01-02` (`t.UTC().Format("2006-01-02")`), как в
charge.full. Порядок строк — всегда `[кредит, списание]`. Кредит выводится
всегда, даже если он равен нулю (нулевая строка легитимна и объяснима; условное
подавление строк усложняет правило и фикстуры).

## Краевые кейсы

- **Апгрейд в первый день периода** (`ev.At == periodStart`): `rem == total`,
  `used == 0`, кредит = полная `st.paid` (весь старый период возвращается).
- **Апгрейд в последний день**: `rem` мал (обычно 1), кредит — небольшая доля,
  строго ≤ `st.paid`.
- **Апгрейд без активной подписки** (`st.plan == nil`): ошибка
  `prorata: upgrade: no active subscription`.
- **Апгрейд на тот же план** (`st.plan.ID == ev.PlanID`): ошибка
  `prorata: upgrade: already on plan "<id>"`.
- **Неизвестный план**: ошибка `prorata: upgrade: unknown plan "<id>"`.
- **Кламп даты нового периода**: апгрейд 31-го на месячный план → конец нового
  периода клампится (31 янв → 28 фев в невисокосный год).
- **Високосный февраль**: знаменатель `total` берётся из фактического
  календарного месяца (29 дней в феврале 2028).
- **Апгрейд после истечения старого периода** (`ev.At ≥ periodEnd`): `rem`
  клампится в 0, кредита нет, новый план списывается полностью.

### Пример 1 (сценарий-витрина PLAN §2, без промо) → golden/02-upgrade-showcase.json

Юзер на pro-month с 1 января, 13-го числа апгрейдится на business-year.
Запрошен новый годовой период (subscribe от 1 января в него не входит).

Пересчёт честно по D1: старый период `[2026-01-01, 2026-02-01)` = **31** день;
остаток `[2026-01-13, 2026-02-01)` = **19** дней; `used = 12`.
`2000.Allocate([12, 19]) = [774, 1226]` → кредит **1226** ($12.26).
(Итог с промо −20% будет посчитан отдельным правилом; здесь промо НЕТ.)


## Табличные тесты (rule_prorate_test.go, пишет mechanic)

Через публичный `Compute` (каталог из примеров). Запрошенный период возьми
широким, чтобы события апгрейда попадали внутрь (например
`2020-01-01T00:00:00Z` → `2030-01-01T00:00:00Z`), кроме кейсов-ошибок, где
инвойс не проверяется.

1. **upgrade без подписки**: одно событие `upgrade business-year` →
   `err != nil`, текст `prorata: upgrade: no active subscription` (инвойс не проверять).
2. **upgrade на тот же план**: `subscribe pro-month`, затем `upgrade pro-month`
   → `err != nil`, текст `prorata: upgrade: already on plan "pro-month"`.
3. **upgrade на неизвестный план**: `subscribe pro-month`, затем
   `upgrade ghost` → `err != nil`, текст `prorata: upgrade: unknown plan "ghost"`.
4. **первый день → полный кредит**: сценарий примера 2 → сумма строк
   `prorate.credit` равна `-2000` (= минус `st.paid`), кредит по модулю равен
   уплаченному (инвариант «кредит ≤ уплаченного», граница равенства).
5. **последний день → кредит строго меньше уплаченного**: сценарий примера 3 →
   `|credit| = 65 < 2000`.
6. **сумма инвойса**: пример 2 → `total_cents == 48000` и равен сумме
   `amount_cents` всех строк (инвариант «деньги не создаются/не исчезают»).

## Gate
