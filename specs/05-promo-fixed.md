# 05-promo-fixed — фиксированный промокод + закон запрета стекования

Тир спеки: architect. Реализация: builder (`rule_promo.go`). Фикстуры/тесты: mechanic.

Ядро для этого правила уже подготовлено architect'ом (коммит
`core(promo): фиксированный промо — Event.AmountCents, pendingPromo.kind, ветка applyPromo`),
симметрично подготовке процентного промо в правиле 04:

- `Event.AmountCents` (`Money`) — фикс-скидка в минорных единицах; в JSON
  прочих событий отсутствует (`omitempty`);
- `pendingPromo` получил дискриминатор `kind` (`promoPercent | promoFixed`) и
  поле `amount Money`;
- хук `applyPromo` в `engine.go` ветвится по `kind`: для `promoFixed` скидка =
  `min(amount, base)` (кламп), строка `promo.fixed`, кламп именует номинал;
- `rulePromoFixed RuleID = "promo.fixed"`.

Builder дописывает **только** фазу 1 в `rule_promo.go` — расширяет `armPromo`:
различает процент/фикс по заполненному полю, валидирует, **взводит**
`state.promo` нужного `kind`. Само применение скидки и строку `promo.fixed`
делает ядро (`applyPromo`), правило её не создаёт. Ядро не трогать.

Это **правило №6 бэклога**: помимо фиксированной скидки оно фиксирует **закон
запрета стекования** — первый конфликт правил в проекте.

## Что делает правило

Фиксированный промокод — одноразовая скидка на **фиксированную сумму** (не
процент) на следующее списание. Механика та же двухфазная, что у процентного
(04); отличается только вычисление скидки во второй фазе и валидация в первой.

**Фаза 1 — взведение (правило `rule_promo.go`, событие `EventApplyPromo`):**

1. Код обязателен: если `ev.Code == ""` → ошибка `prorata: promo: empty code`.
2. Взаимоисключение полей: если заданы **оба** — `ev.Bps != 0` **и**
   `ev.AmountCents != 0` → ошибка `prorata: promo: both bps and amount set`.
3. Выбор вида по заполненному полю:
   - `ev.AmountCents != 0` → **фиксированный**. Если `ev.AmountCents < 0` →
     ошибка `prorata: promo: negative amount <n>` (`<n>` = `ev.AmountCents` как
     целое число центов). Иначе
     `st.promo = pendingPromo{armed: true, kind: promoFixed, amount: ev.AmountCents, code: ev.Code}`.
   - иначе (`ev.AmountCents == 0`) → **процентный** (поведение правила 04): при
     `ev.Bps < 0 || ev.Bps > 10000` → ошибка
     `prorata: promo: bps <n> out of range [0,10000]`; иначе
     `st.promo = pendingPromo{armed: true, kind: promoPercent, bps: ev.Bps, code: ev.Code}`.
4. **Закон стекования** (одноразовость на взведении): если промо уже взведён и
   ещё не сгорел (`st.promo.armed`) → ошибка
   `prorata: promo: promo already pending`. Проверка **kind-агностична** — ловит
   и фикс-поверх-процента, и процент-поверх-фикса, и фикс-поверх-фикса единым
   условием (см. D3). Порядок проверок как в 04: сперва корректность самого
   события (1–3), затем стек-гард (4).
5. Правило **не возвращает строк** (`nil, nil`). Активная подписка НЕ требуется
   (симметрия с 04, D5).

**Фаза 2 — применение (ядро `applyPromo`, для каждого события после его правила):**

1. Если промо не взведён (`!st.promo.armed`) — ничего не делает.
2. `base` = сумма **положительных** `Amount` строк события (валовой заряд).
   Отрицательные строки (кредит остатка) в базу не входят.
3. Если `base <= 0` — ничего не делает, промо **остаётся взведён** (ждёт первого
   реального заряда).
4. Иначе по `kind`:
   - `promoFixed`: `applied = min(amount, base)` (**кламп**); строка `promo.fixed`
     с `Amount = -applied`; промо **сжигается** (`st.promo = pendingPromo{}`).
   - `promoPercent`: как в 04 (`base.Percent(bps)`, строка `promo.percent`).

`applyPromo` выполняется **до** `applyCredit` — кредитный баланс гасит уже
удешевлённый чистый заряд (симметрия с 04, D2). Как и в 04, хук отрабатывает и
для событий вне запрошенного периода (леджер промо согласован через границу);
строка попадает в инвойс только для событий внутри периода.

## Ключевые решения (решение → почему → отвергнутая альтернатива)

### D1. Модель — то же событие `apply_promo`, вид промо по заполненному полю `AmountCents`/`Bps`

**Решение:** фиксированный промо — **не** новое событие, а тот же
`EventApplyPromo` с суммой в `Event.AmountCents` (минорные единицы). Вид скидки
определяется тем, какое поле заполнено: `AmountCents != 0` → фикс, иначе →
процент. Взаимоисключение «либо `Bps`, либо `AmountCents`, не оба» — валидация
корректности одного события (ошибка `both bps and amount set`), а **не** закон
стекования.

**Почему:** «промо» — одна доменная сущность (одноразовая скидка на следующий
заряд) с двумя способами задать величину. Один тип события держит модель узкой
(`[]Event` не растёт), одно состояние `pendingPromo` с дискриминатором `kind`
позволяет одному движковому хуку `applyPromo` обслуживать оба вида, а закону
стекования (D3) — работать единообразно для любых пар видов. Взаимоисключение на
уровне поля исключает бессмысленный «процент И фикс одновременно» ещё до
взведения.

**Отвергнуто:** отдельное событие `EventApplyPromoFixed` + своё состояние —
дублирует хук, ломает kind-агностичный закон стекования (пришлось бы сверять два
разных pending), раздувает событийную модель ради одного числа. Поле `Kind`-строка
в событии вместо «вид по заполненному полю» — лишняя валидация «kind совпадает с
непустым полем», третья точка рассинхрона.

### D2. Применение — кламп `min(amount, base)`, до кредитного баланса, только на положительные заряды

**Решение:** фиксированная скидка применяется к **первому положительному заряду**
события (валовому `base`), но **не более самого заряда**:
`applied = min(amount, base)`. Хук стоит **до** `applyCredit` (симметрия с 04);
отрицательные строки (кредит остатка апгрейда) не удешевляются.

**Почему:** фикс-скидка больше заряда не должна создавать деньги/фантомный refund
— кламп держит инвариант «сумма не уходит в минус от одной скидки» и «кредит ≤
уплаченного» так же, как `Money.Percent` держит его для процента (|скидка| ≤
база). Порядок до баланса — чтобы предоплата гасила уже удешевлённый нетто, а не
сгорала против части, которую покрыла скидка (пример 4 доказывает: `credit.applied`
считается по `base − applied`). Скидка на положительные строки — «−N денег с того,
что списывают», а не с возврата.

**Отвергнуто:** без клампа (скидка = `amount`, заряд уходит в минус на разницу) —
рвёт инвариант «деньги не создаются», фикс-100500 превратил бы дешёвый заряд в
refund; скидка ПОСЛЕ баланса — предоплата сгорает против покрытой скидкой части,
итог может уйти в минус (тот же дефект, что отвергнут в 04 D2); распределение фикса
по нескольким зарядам события — у события один валовой `base`, дробить нечего.

### D3. Закон запрета стекования — kind-агностичный `already pending`, живёт в `armPromo`

**Решение:** **закон стекования** — «пока взведённый промо не сгорел, второй
`apply_promo` любого вида недопустим» → ошибка
`prorata: promo: promo already pending`. Он живёт в **одной точке** — проверке
`st.promo.armed` в `armPromo` (фаза 1), и она **не смотрит на `kind`**, поэтому
единым условием запрещает все пары: процент+процент (уже из 04 D6),
процент+фикс, фикс+процент, фикс+фикс. Последовательные промо, каждый из которых
успел сгореть до следующего (появился заряд между ними), легальны: «одноразовый»
= «применяется один раз», а не «за историю один».

**Почему:** стекование — это **композиция двух скидок на один заряд**; её
семантика неоднозначна (что раньше — процент от суммы или минус фикс? компаундинг
или нет?), а бэклог №6 требует именно **запрет**, не композицию. Держать закон в
одной kind-агностичной проверке — единственный способ, чтобы новый вид промо
(фикс) получил запрет стекования «бесплатно», без комбинаторного разрастания
правил «X поверх Y». `armed`-флаг уже есть — закон — это его прочтение, а не новый
механизм.

**Отвергнуто:** композиция/суммирование двух скидок — вне скоупа №6, порядок
компаундирования неоднозначен, легко создаёт refund; «последний побеждает»
(замена) — молча теряет первый промо; отдельные проверки на каждую пару видов
(`percentOverFixed`, `fixedOverPercent`, …) — комбинаторный взрыв, каждый новый
вид ×2 правила, тогда как kind-агностичная одна проверка не растёт.

### D4. Description — фактически применённая сумма; при клампе именуется номинал

**Решение:** строка `promo.fixed` в `Description` показывает **фактически
применённую** скидку (`applied`), не номинал. Формат без клампа
(`amount <= base`): `<code>: -<applied> off <base>`; при клампе
(`amount > base`): `<code>: -<applied> off <base> (capped from <nominal>)`, где
`<applied> == <base>`. `Amount` строки всегда `= -applied` (`≤ 0`, `|·| ≤ base`).

**Почему:** инвариант «каждая строка объясняет себя»: в леджер идёт то, что
реально списано (`applied`), поэтому его и показываем — как строка `promo.percent`
показывает реально вычисленную скидку. Кламп — самый интересный краевой случай
фикса, и он должен быть **виден в самой строке**: суффикс `(capped from …)`
объясняет, почему списано меньше номинала, не пряча номинал в спеку. Без клампа
суффикс не нужен — форма остаётся чистой и симметричной проценту.

**Отвергнуто:** показывать всегда номинал (`-<amount>`), а `Amount` брать
клампнутый — строка «−50.00» при списании 20.00 рвёт «строка объясняет сумму
Amount»; всегда добавлять `(capped from …)` даже без клампа — шум в 99% строк,
где номинал == применённому.

### D5. Округления нет — фикс задан в центах

**Решение:** для фиксированного промо арифметики округления **нет**: скидка уже в
минорных единицах, `applied = min(amount, base)` — целочисленный `min` без
деления. `Money.Percent`/`formatPercent` в фикс-ветке не участвуют.

**Почему:** нечего округлять — нет деления/процента. Инвариант округления (D1
ядра) касается только процентной ветки и правил proration; фикс к нему
ортогонален. Отмечаю явно, чтобы гейт не искал стратегию округления там, где её
нет.

**Отвергнуто:** (нет альтернатив — округлять нечего).

## Инвариант «деньги не создаются, кредит ≤ уплаченного» при фикс-промо

- `promo.fixed` всегда `≤ 0` и по модулю `≤ base` (кламп `min(amount, base)`).
  Скидка не может превратить одиночный положительный заряд в отрицательный —
  фикс-промо сам по себе не порождает refund, даже при `amount ≫ base`.
- Скидка не трогает `creditBalance`. `applyCredit` берёт
  `applied = min(net, balance)` по **удешевлённому** `net` — «кредит ≤
  уплаченного» лишь усиливается (симметрия с 04).
- `Total = Σ строк` считает ядро; фикс-скидка — обычная строка, деньги не
  теряются.

## RuleID и формат строк

| строка | RuleID | Description | Amount | источник |
|---|---|---|---|---|
| фикс-скидка без клампа | `promo.fixed` | `<code>: -<applied> off <base>` | `-applied` (`= -amount`) | ядро (`applyPromo`) |
| фикс-скидка с клампом | `promo.fixed` | `<code>: -<applied> off <base> (capped from <nominal>)` | `-applied` (`= -base`) | ядро (`applyPromo`) |

- `<code>` — `ev.Code` как есть.
- `<applied>` — `min(amount, base)` через `Money.String` (`"5.00"`, `"20.00"`).
- `<base>` — валовой положительный заряд через `Money.String` (`"20.00"`,
  `"480.00"`).
- `<nominal>` — исходный `amount` через `Money.String` (только в клампнутой
  форме, `amount > base`).
- Правило `rule_promo.go` строк не порождает (`nil, nil`).

## Краевые кейсы

- **Фикс больше заряда (кламп)** (D2, D4): `applied = base`, строка с суффиксом
  `(capped from <nominal>)`, чистый заряд события до баланса — ноль. Пример 2.
- **Фикс поверх несгоревшего процента** (стекование, D3): ошибка
  `prorata: promo: promo already pending`. Пример 5.
- **Процент поверх несгоревшего фикса** (стекование, D3): та же ошибка
  (симметрично). Табличный кейс 8.
- **Фикс поверх несгоревшего фикса** (стекование, D3): та же ошибка. Табличный
  кейс 9.
- **Оба поля заданы** (`Bps != 0` и `AmountCents != 0`): ошибка
  `prorata: promo: both bps and amount set`. Пример 6.
- **Отрицательный фикс** (`AmountCents < 0`): ошибка
  `prorata: promo: negative amount <n>`.
- **Пустой код**: ошибка `prorata: promo: empty code` (как в 04).
- **Фикс 0** (`AmountCents == 0`): полем не отличим от процента-0 (оба поля
  нулевые) → трактуется как **процент-0** (существующее поведение 04: строка
  `promo.percent` с `Amount = 0`, промо сгорает). Отдельного `promo.fixed` с
  нулём модель не выражает — и это ок: экономически он идентичен нулевой
  строке, деньги те же. Чтобы задать фикс, `AmountCents` должен быть `> 0`.
- **Фикс до subscribe** (симметрия с 04 D5): взводится, применяется к первому
  заряду — самому `subscribe`. Пример 1.
- **Фикс не удешевляет кредит остатка**: скидка по валовому положительному
  заряду; отрицательные строки (`prorate.credit`) не тронуты. Пример 3.
- **Фикс + кредитный баланс**: скидка ДО `credit.applied`, баланс гасит
  удешевлённый нетто. Пример 4.
- **Событие-потребитель вне запрошенного периода**: промо всё равно сгорает,
  строка `promo.fixed` в инвойс не попадает.
- **Фикс взведён, но следующее событие без положительного заряда**: промо не
  сгорает, ждёт первого заряда.

## Примеры вход→выход (точные значения — фикстуры строить байт-в-байт)

### Пример 1 (фикс до подписки — скидка на первый заряд, без клампа) → golden/05-fixed-subscribe.json

`apply_promo FIVEOFF` (фикс −$5.00, `amount_cents = 500`) взводится до
`subscribe pro-month` (оба 2026-01-01). Применяется к самому `subscribe`:
`base = 2000`, `applied = min(500, 2000) = 500` → `promo.fixed = −500`
(`FIVEOFF: -5.00 off 20.00`). Итог `2000 − 500 = 1500`.

Вход:
```json
{
  "name": "05-fixed-subscribe",
  "catalog": [
    {"id": "pro-month", "price_cents": 2000, "interval": "month", "currency": "USD"}
  ],
  "events": [
    {"at": "2026-01-01T00:00:00Z", "type": "apply_promo", "amount_cents": 500, "code": "FIVEOFF"},
    {"at": "2026-01-01T00:00:00Z", "type": "subscribe", "plan": "pro-month"}
  ],
  "period": {"start": "2026-01-01T00:00:00Z", "end": "2026-02-01T00:00:00Z"}
}
```

Выход:
```json
{
  "currency": "USD",
  "lines": [
    {"rule": "charge.full", "description": "pro-month: full period 2026-01-01 to 2026-02-01", "amount_cents": 2000},
    {"rule": "promo.fixed", "description": "FIVEOFF: -5.00 off 20.00", "amount_cents": -500}
  ],
  "total_cents": 1500
}
```

### Пример 3 (фикс + апгрейд — скидка на заряд нового плана, кредит остатка не тронут) → golden/05-fixed-upgrade.json

Юзер на pro-month с 1 января, 13-го апгрейдится на business-year, применив
одноразовый фикс `TENOFF` (−$10.00, `amount_cents = 1000`) перед апгрейдом.
Пересчёт proration как в 04/02: старый период `[2026-01-01, 2026-02-01)` = **31**
день, остаток **19** дней, `used = 12`; `2000.Allocate([12, 19]) = [774, 1226]`
→ кредит **1226**. Скидка: `base = 48000`, `applied = min(1000, 48000) = 1000` →
`promo.fixed = −1000` (`TENOFF: -10.00 off 480.00`). Кредит остатка (`−1226`) не
удешевляется. Итог: `−1226 + 48000 − 1000 = 45774`. Кредитного баланса нет
(даунгрейда не было).

Запрошенный период — с даты апгрейда; subscribe (1 января) в него не входит.

Вход:
```json
{
  "name": "05-fixed-upgrade",
  "catalog": [
    {"id": "pro-month", "price_cents": 2000, "interval": "month", "currency": "USD"},
    {"id": "business-year", "price_cents": 48000, "interval": "year", "currency": "USD"}
  ],
  "events": [
    {"at": "2026-01-01T00:00:00Z", "type": "subscribe", "plan": "pro-month"},
    {"at": "2026-01-13T00:00:00Z", "type": "apply_promo", "amount_cents": 1000, "code": "TENOFF"},
    {"at": "2026-01-13T00:00:00Z", "type": "upgrade", "plan": "business-year"}
  ],
  "period": {"start": "2026-01-13T00:00:00Z", "end": "2027-01-13T00:00:00Z"}
}
```

### Пример 4 (фикс + даунгрейд — скидка ДО кредитного баланса) → golden/05-fixed-downgrade-order.json

Subscribe team-month 1 января, `apply_promo SAVE5` (фикс −$5.00,
`amount_cents = 500`) и downgrade на pro-month 13 января. Даунгрейд банкует
остаток team: период `[2026-01-01, 2026-02-01)` = **31** день, остаток **19**,

pro-month `+2000`, период `[2026-01-13, 2026-02-13)`.

**1565** (в инвойсе не виден). Если бы баланс шёл ДО скидки, `credit.applied`
было бы −2000, а итог −500 (фантомный refund) — кейс фиксирует порядок.

## Табличные тесты (rule_promo_test.go, дописывает mechanic)

Через публичный `Compute` (каталоги из примеров). Для не-ошибочных кейсов бери
период, покрывающий события; для ошибочных инвойс не проверяется.

1. **фикс на первый заряд (без клампа)**: сценарий примера 1 → строка
   `promo.fixed` с `amount_cents == -500`, `total_cents == 1500`,
   description `FIVEOFF: -5.00 off 20.00`.
2. **кламп (фикс > заряда)**: сценарий примера 2 → `promo.fixed == -2000`
   (`= -base`), `total_cents == 0`, description с суффиксом
   `(capped from 50.00)`.
3. **фикс не удешевляет кредит остатка**: сценарий примера 3 → `prorate.credit`
   остался `-1226`, `promo.fixed == -1000`, `total_cents == 45774`.
4. **фикс ДО баланса (порядок)**: сценарий примера 4 → `credit.applied == -1500`
   (по удешевлённому нетто, не −2000), `total_cents == 0`, единственные
   отрицательные строки — `promo.fixed` и `credit.applied`.
5. **сумма инвойса**: пример 3 → `total_cents` равен сумме всех `amount_cents`
   строк (деньги не создаются/не исчезают).
6. **оба поля заданы**: сценарий примера 6 → `err != nil`, текст
   `prorata: promo: both bps and amount set`.
7. **стекование фикс-поверх-процента**: сценарий примера 5 → `err != nil`, текст
   `prorata: promo: promo already pending`.
8. **стекование процент-поверх-фикса**: `apply_promo amount_cents=500 code="F"`,
   затем `apply_promo bps=2000 code="P"`, заряда между ними нет → `err != nil`,
   текст `prorata: promo: promo already pending`.
9. **стекование фикс-поверх-фикса**: два `apply_promo` с `amount_cents` подряд
   без заряда между ними → `err != nil`, текст
   `prorata: promo: promo already pending`.
10. **отрицательный фикс**: `apply_promo amount_cents=-100 code="X"` → `err !=
    nil`, текст `prorata: promo: negative amount -100`.
