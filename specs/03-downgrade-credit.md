# 03-downgrade-credit — даунгрейд с кредитным балансом (не refund)

Тир спеки: architect. Реализация: builder (`rule_downgrade.go`). Фикстуры/тесты: mechanic.

Ядро для этого правила уже подготовлено architect'ом (коммит `core(downgrade)`):
поле `state.creditBalance`, тип `EventDowngrade`, применение баланса движком
(`applyCredit`, RuleID `credit.applied`). Builder пишет **только**
`rule_downgrade.go` — банкует остаток и возвращает строку заряда нового плана;
ядро не трогает.

## Что делает правило

Обрабатывает `EventDowngrade`: смену активной подписки на другой (обычно более
дешёвый) план посреди текущего биллинг-периода. В отличие от апгрейда (правило
02), неиспользованный остаток старого плана **не возвращается отрицательной
строкой-refund**, а **банкуется в кредитный баланс** подписки. Баланс движок
применяет к будущим (и к собственному) зарядам строкой `credit.applied`.

Поведение по шагам (правило `rule_downgrade.go`):

1. Активная подписка обязательна. Если `st.plan == nil` → ошибка
   `prorata: downgrade: no active subscription`.
2. Новый план берётся из каталога по `ev.PlanID`. Неизвестный →
   `prorata: downgrade: unknown plan "<id>"`.
3. Даунгрейд на тот же план запрещён: если `st.plan.ID == ev.PlanID` →
   `prorata: downgrade: already on plan "<id>"`.
4. Считается остаток старого плана (формула — D2 ниже) и **прибавляется** к
   `st.creditBalance`. Отдельной строки на банкование НЕ создаётся.
5. Считается новый период: `[ev.At, AddInterval(ev.At, newPlan.Interval))` —
   кламп дня по D3 из specs/00-core.md.
6. Состояние переписывается на новый план: `plan = newPlan`,
   `periodStart = ev.At`, `periodEnd = newEnd`, `paid = newPlan.Price`.
   `creditBalance` — накопительное, из шага 4, не сбрасывается.
7. Возвращается **одна** строка: заряд нового плана в полном объёме
   (`downgrade.charge`, `+newPlan.Price`).

После возврата строк движок (ядро, `applyCredit`) применяет `creditBalance` к
чистому положительному заряду события — см. D3. Это единый механизм для всех
правил, правило `rule_downgrade.go` его не реализует.

## Ключевые решения (решение → почему → отвергнутая альтернатива)

### D1. Новый план вступает в силу немедленно, с момента события

**Решение:** даунгрейд применяется мгновенно в `ev.At` — новый план активен
сразу, старый период закрывается ровно как при апгрейде (правило 02). Даунгрейд
не откладывается до конца текущего периода.

**Почему:** это единственная модель, дающая **кредитный баланс** (решение
бэклога №4). Симметрия с апгрейдом делает событийную модель однородной: оба
события — «смена плана посреди периода», отличаются лишь судьбой остатка (refund
vs банк). Фолд событий в состояние остаётся детерминированным и без «часов».

**Отвергнуто:** отложенный даунгрейд (новый план со следующего периода, без
proration) — так делает Stripe по умолчанию, но: (а) остатка нет, банковать
нечего → правило перестаёт быть «кредитным балансом» и противоречит бэклогу;
(б) движку пришлось бы моделировать *запланированную будущую* смену плана, а в
модели «свёртка `[]Event` в состояние» нет часов между событиями — это тяжёлая
переделка ядра ради поведения, которое витрине не нужно.

### D2. Остаток банкуется в баланс, не возвращается строкой; формула — как в правиле 02

**Решение:** остаток = **вторая доля** от `st.paid.Allocate([]int64{used, rem})`
(та же формула наибольших остатков, что D1 правила 02: `total = Days(старый
период)`, `rem = max(Days([ev.At, oldPeriodEnd]), 0)`, `used = total - rem`).
Эта величина **прибавляется к `st.creditBalance`** и **не** попадает в инвойс
отдельной строкой. Refund-строки (отрицательной) даунгрейд не порождает.

**Почему:** дословный бэклог — «не возвращает деньги строкой, кладёт остаток в
кредитный баланс». Отсутствие отрицательной строки гарантирует, что даунгрейд
сам по себе **не может увести итог инвойса в минус** (нет выплаты кэшем).
Переиспользование allocation-формулы правила 02 сохраняет инвариант «остаток ≤
уплаченного» по построению (`parts[1] ≤ st.paid`) и не теряет копейку (D2 ядра).

**Отвергнуто:**
- Отрицательная строка-refund (как `prorate.credit`) — это **и есть** refund,
  прямо противоречит бэклогу; при дешёвом новом плане уводит `Total` в минус
  (возврат кэшем), чего кредитный баланс избегает.
- Двойная запись `downgrade.credit −c` + `credit.banked +c` (в сумме ноль) —
  «честный» double-entry, но `+c` читается наивным клиентом как фантомный заряд,
  шумит в инвойсе и усложняет фикстуры без пользы для витрины.
- Информационная строка банкования с `amount_cents: 0` — число в тексте
  расходится с нулевой суммой; провенанс банка документируем в спеке, а не в
  каждой строке.

### D3. Применение баланса — движком, единой строкой `credit.applied`, к заряду любого правила

**Решение:** применяет баланс **ядро** (`applyCredit` в engine.go), а не правило.
После каждого события движок считает `net = Σ amount` строк события; если
`net > 0` и `creditBalance > 0`, списывает `applied = min(net, creditBalance)`,
уменьшает баланс и добавляет **одну** строку
`{RuleID: "credit.applied", Description: "credit balance applied", Amount: -applied}`.
Применение **жадное**: включает собственный заряд события-даунгрейда (баланс
доступен сразу после банкования того же события). Баланс мутируется для **всех**
событий, в т.ч. вне запрошенного периода, чтобы леджер был согласован через
границу периода; строка в инвойс попадает только для событий внутри периода.

**Почему:** баланс — сквозная леджер-механика, а не биллинг-правило; его место в
ядре, рядом с подсчётом `Total`. Единый движковый механизм означает, что баланс
гасит заряд **любого** правила (subscribe/upgrade/downgrade) без правки этих
правил и без запрещённого `helpers.go`. Жадное применение не заставляет клиента
платить кэшем за новый план, пока на балансе лежит его же предоплата; излишек
переходит на следующие события — так удовлетворяется «погашает будущие
списания».

**Отвергнуто:**
- Применение внутри каждого правила-заряда — дублирует логику в
  `rule_charge`/`rule_prorate`/`rule_downgrade` либо требует общего хелпера
  (запрещён) и правки правила 02 (вне скоупа даунгрейда).
- Отложенное применение (баланс не гасит собственный заряд даунгрейда, только
  следующие события) — заставляет платить кэшем за новый план при лежащем
  балансе, экономически странно.
- Провенанс в тексте `credit.applied` (из какого даунгрейда деньги) — движок
  видит только `Money`, источник ему недоступен без протаскивания контекста
  через ядро; сознательно упрощено до фиксированного описания.

### D4. Состояние после даунгрейда — новый план, `paid = newPlan.Price`, баланс отдельно

**Решение:** `paid` становится **полной ценой нового плана** (как D4 правила 02),
периодные поля перезаписываются. `creditBalance` — самостоятельное накопительное
поле, к `paid` не примешивается.

**Почему:** `paid` — база для будущих proration-кредитов; она должна отражать
стоимость *нового* периода, а не остаток старого. Разделение `paid` и
`creditBalance` держит инвариант «кредит ≤ уплаченного» честным при цепочках
(апгрейд после даунгрейда считает остаток от новой `paid`, а банк живёт отдельно).

**Отвергнуто:** `paid = newPlan.Price − applied` (занижает базу будущего кредита);
складывать банк в `paid` (смешивает две разные величины, ломает формулу остатка).

### D5. Правило механическое, цены не сравнивает

**Решение:** правило не проверяет, дешевле новый план или дороже. «Апгрейд vs
даунгрейд» выбирает вызывающий через `EventType`. Единственный семантический
запрет — тот же план (шаг 3). Даунгрейд на **более дорогой** план не ошибка: он
механически банкует остаток и заряжает новый (дорогой) план.

**Почему:** прямое наследование D5 правила 02. «Дороже» неоднозначно при смене
интервала ($20/мес vs $480/год); связывать логику с порядком цен — хрупкость без
пользы. Ответственность за выбор события — на вызывающем.

**Отвергнуто:** требовать `newPrice ≤ oldPrice` (ломается на смене интервала,
дублирует ответственность и расходится с симметричным правилом 02).

## Инвариант «кредит ≤ фактически уплаченного» — формулировка на уровне леджера

Банкуется всегда `parts[1] ≤ st.paid` (доля от реально уплаченного за период).
Применяется всегда `applied = min(net, creditBalance) ≤ creditBalance`, поэтому
`creditBalance ≥ 0` в любой момент. Отсюда:

```
Σ credit.applied  ≤  Σ banked  ≤  Σ paid
```

Ни одна строка `credit.applied` и никакая их сумма не превышают того, что было
предоплачено. Баланс — не источник новых денег, а перенос уже уплаченного.

## RuleID и формат строк

| строка | RuleID | Description | Amount | источник |
|---|---|---|---|---|
| заряд нового плана | `downgrade.charge` | `<newPlan.ID>: full period <ev.At> to <newEnd>` | `+newPlan.Price` | `rule_downgrade.go` |
| применение баланса | `credit.applied` | `credit balance applied` (фикс.) | `-applied` (< 0) | ядро (`applyCredit`) |

Банкование остатка строки НЕ порождает. Даты — UTC формата `2006-01-02`
(`t.UTC().Format("2006-01-02")`), как в charge.full/prorate.charge. Порядок
внутри события-даунгрейда: сначала `downgrade.charge`, затем (если баланс
сработал) `credit.applied`.

## Краевые кейсы

- **Даунгрейд в первый день** (`ev.At == periodStart`): `rem == total`, `used == 0`,
  банкуется вся `st.paid` (весь старый платёж). Пример 2.
- **Даунгрейд в последний день**: `rem` мал (обычно 1), банк — небольшая доля,
  строго ≤ `st.paid`; нового заряда баланс покрывает лишь часть, разница платится
  кэшем. Пример 3.
- **Даунгрейд без активной подписки** (`st.plan == nil`): ошибка
  `prorata: downgrade: no active subscription`.
- **Даунгрейд на тот же план** (`st.plan.ID == ev.PlanID`): ошибка
  `prorata: downgrade: already on plan "<id>"`.
- **Неизвестный план**: ошибка `prorata: downgrade: unknown plan "<id>"`.
- **Даунгрейд на более дорогой план**: не ошибка (D5) — банкует остаток, заряжает
  дорогой план, баланс гасит сколько хватает.
- **Даунгрейд после истечения старого периода** (`ev.At ≥ periodEnd`): `rem`
  клампится в 0, банкуется 0, новый план заряжается полностью, гасить нечем.
  Пример 5.
- **Кламп даты нового периода**: даунгрейд 31-го на месячный план → конец нового
  периода клампится (31 янв → 28 фев в невисокосный год). Пример 3.
- **Апгрейд после даунгрейда** (взаимодействие с правилом 02): правило 02 считает
  остаток от новой `st.paid` (цена дешёвого плана), а движок гасит его заряд из
  банка, оставшегося после даунгрейда. Пример 4.

### Пример 1 (даунгрейд посреди периода, кредит покрывает новый заряд) → golden/03-downgrade-covers-charge.json

Subscribe team-month 1 января, downgrade на pro-month 13 января. Старый период
`[2026-01-01, 2026-02-01)` = **31** день; остаток `[2026-01-13, 2026-02-01)` =
**19** дней, `used = 12`. `5000.Allocate([12, 19]) = [1935, 3065]` → банкуется
**3065** ($30.65). Новый период pro-month `[2026-01-13, 2026-02-13)`, заряд
**2000**. Движок гасит из банка `min(2000, 3065) = 2000`; на балансе остаётся
**1065** (в инвойсе не виден). Запрошенный период начинается с даты даунгрейда —
subscribe (1 января) в него не входит, строит только состояние.

Вход:
```json
{
  "name": "03-downgrade-covers-charge",
  "catalog": [
    {"id": "pro-month", "price_cents": 2000, "interval": "month", "currency": "USD"},
    {"id": "team-month", "price_cents": 5000, "interval": "month", "currency": "USD"}

    {"at": "2026-01-01T00:00:00Z", "type": "subscribe", "plan": "team-month"},

  "period": {"start": "2026-01-13T00:00:00Z", "end": "2026-03-01T00:00:00Z"}

```

```json

  "currency": "USD",
```

### Пример 4 (цепочка: subscribe → downgrade → upgrade, банк гасит будущий заряд) → golden/03-downgrade-then-upgrade.json

Subscribe business-year 1 января (paid **48000**, период `[2026-01-01, 2027-01-01)`
= **365** дней). Downgrade на pro-month 13 января: остаток
`[2026-01-13, 2027-01-01)` = **353** дня, `used = 12`,
`48000.Allocate([12, 353]) = [1578, 46422]` → банкуется **46422**. Новый период
pro-month `[2026-01-13, 2026-02-13)`, заряд **2000**, гасится из банка →
баланс **44422**. `st.paid = 2000`.

Затем upgrade на business-year 20 января (правило 02): старый период
`[2026-01-13, 2026-02-13)` = **31** день, остаток `[2026-01-20, 2026-02-13)` =
**24** дня, `used = 7`, `2000.Allocate([7, 24]) = [452, 1548]` → `prorate.credit`
**−1548**; `prorate.charge` business-year **+48000**, период
`[2026-01-20, 2027-01-20)`. Чистый заряд события апгрейда `net = 48000 − 1548 =
46452`; банк гасит `min(46452, 44422) = 44422` → `credit.applied` **−44422**,
баланс обнуляется, **2030** платится кэшем.

Запрошенный период `[2026-01-13, 2027-06-01)` покрывает downgrade и upgrade;
subscribe (1 января) строит состояние, в инвойс не входит.

## Табличные тесты (rule_downgrade_test.go, пишет mechanic)

Через публичный `Compute` (каталог из примеров). Для не-ошибочных кейсов бери
широкий период (например `2020-01-01T00:00:00Z` → `2030-01-01T00:00:00Z`), чтобы
события попадали внутрь; для ошибочных инвойс не проверяется.

1. **downgrade без подписки**: одно событие `downgrade pro-month` →
   `err != nil`, текст `prorata: downgrade: no active subscription`.
2. **downgrade на тот же план**: `subscribe pro-month`, затем `downgrade pro-month`
   → `err != nil`, текст `prorata: downgrade: already on plan "pro-month"`.
3. **downgrade на неизвестный план**: `subscribe team-month`, затем
   `downgrade ghost` → `err != nil`, текст `prorata: downgrade: unknown plan "ghost"`.
4. **банк не уходит в refund**: сценарий примера 1 → `total_cents == 0` (не
   отрицательный); в инвойсе нет строки с `amount_cents < 0`, кроме
   `credit.applied`; сумма всех `amount_cents` равна `total_cents` (деньги не
   создаются/не исчезают).
5. **первый день → банкуется весь платёж**: сценарий примера 2 → сумма всех
   `credit.applied` по модулю (2000) ≤ уплаченного за старый план (5000), и
   строка `charge.full team-month` присутствует со знаком `+5000`.
6. **банк ≤ уплаченного в цепочке**: сценарий примера 4 → `Σ |credit.applied| ==
   46422` и `≤` сумме всех положительных зарядов старых планов; `total_cents == 2030`.
7. **истечение → банк 0**: сценарий примера 5 → в инвойсе ровно одна строка
   `downgrade.charge` (+2000), нет строки `credit.applied`, `total_cents == 2000`.
