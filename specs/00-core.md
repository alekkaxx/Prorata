# 00-core — ядро prorata

Тир: architect. Формат каждого пункта: **решение → почему → отвергнутая альтернатива**.

## D1. Money — int64 минорных единиц

**Решение:** `type Money int64`, суммы в центах. Округление везде — **half away from zero** («коммерческое»: 1.5 → 2, −1.5 → −2). Проценты передаются в базисных пунктах (`bps int64`, 10000 = 100%) — float в API денег не существует.

**Почему:** half away from zero симметрично по знаку и объяснимо клиенту одной фразой; объяснимость — инвариант проекта. Базисные пункты убирают float и дают точность до 0.01%.

**Отвергнуто:** float64 (накопление ошибок — дисквалификация в биллинге); банковское округление half-even (статистически честнее на больших потоках, но требует абзаца объяснений в каждом спорном инвойсе — цена выше выгоды при наших объёмах).

## D2. Allocation — largest remainder, копейка не теряется

**Решение:** `Money.Allocate(weights []int64) ([]Money, error)` — метод наибольших остатков: каждой части floor(m·w/W), оставшиеся центы раздаются частям с наибольшим дробным остатком, при равенстве — меньший индекс. **Сумма частей всегда равна исходной сумме** — это главный инвариант движка. Отрицательные суммы зеркалятся (аллоцируется модуль, части отрицаются). Ошибки: пустые weights, отрицательный вес, нулевая сумма весов.

**Почему:** proration и разбиение VAT сводятся к «раздели сумму по весам без потери копейки»; largest remainder — стандартный способ с гарантией суммы и минимальным отклонением от пропорции (< 1 цент на часть).

**Отвергнуто:** независимое округление каждой части (классическая ловушка: сумма частей ≠ исходной — прямое нарушение инварианта); «весь остаток последней части» (систематически искажает последнюю строку, необъяснимо).

## D3. Period — полуинтервал, дни, календарный месяц с клампом

**Решение:** `Period{Start, End}` — полуинтервал `[Start, End)`. Гранулярность proration — **дни** (день = 24h, счёт полных суток). Биллинг-период: календарный месяц/год от якорной даты с **клампом дня** (31 янв + месяц = 28/29 фев; 29 фев + год = 28 фев). Год = 12 месяцев. Даты в фикстурах и описаниях — UTC.

**Почему:** дни — та точность, которую человек может проверить в инвойсе руками; полуинтервал убирает двусмысленность границ (конец одного периода == старт следующего, ни один день не посчитан дважды); кламп от якоря — поведение, которое пользователи знают по Stripe.

**Отвергнуто:** секундная гранулярность (ложная точность, фикстуры нечитаемы); месяц = 30 дней (дрейф якорной даты, «31 декабря − 30 дней» рвёт календарную интуицию).

## D4. Событийная модель и регистрация правил

**Решение:** вход движка — `[]Event`, отсортированный по времени (нарушение порядка = ошибка, движок не сортирует сам). `Compute` фолдит события в состояние подписки; строки инвойса генерят правила. Правило = файл `rule_*.go`, регистрирующий обработчик своего `EventType` через `registerRule` в `init()`. Строки попадают в инвойс только от событий внутри запрошенного периода; события до периода лишь строят состояние.

**Почему:** детерминированный фолд даёт идемпотентность бесплатно; регистрация через `init()` означает, что builder добавляет правило, **не редактируя ядро** — конвенция «ядро только через architect» обеспечена механически, а не дисциплиной.

**Отвергнуто:** молчаливая сортировка входа движком (маскирует баг у вызывающего); явная dispatch-таблица в engine.go (каждое правило = правка ядра builder'ом); правила-интерфейсы с саморегистрацией через рефлексию (магия без выгоды).

## D5. Invoice — каждая строка объясняет себя

**Решение:** `Line{RuleID, Description, Amount}`; `Invoice{Currency, Lines, Total}`, Total = сумма строк. Движок **возвращает ошибку**, если правило породило строку с пустым RuleID или Description. Валюта одна на каталог (смешение валют в каталоге = ошибка валидации). Формат Description задаёт спека каждого правила, ядро требует лишь непустоту.

**Почему:** «инвойс, который не может объясниться, — баг» из PLAN превращено из декларации в проверку рантайма.

**Отвергнуто:** Description как best effort (инвариант, который не проверяется, — не инвариант); мультивалютность (вне скоупа по PLAN).

## D6. Детерминизм — проверяется, не декларируется

**Решение:** `Compute` — чистая функция. Golden-раннер гоняет каждую фикстуру **дважды** и сравнивает JSON-байты между прогонами и с эталоном.

**Почему:** идемпотентность — инвариант; двойной прогон ловит скрытую недетерминированность (порядок map и т.п.) даром.

**Отвергнуто:** отдельный property-тест идемпотентности на случайных событиях — отложен до появления генераторов случайных валидных историй (сейчас событие одно, тест был бы тавтологией).

## Публичный API (итог)

```go
type Money int64                                  // minor units
func (m Money) Allocate(weights []int64) ([]Money, error)
func (m Money) Percent(bps int64) Money           // half away from zero
func (m Money) String() string                    // "12.34", "-0.05"

type Interval string                              // IntervalMonth | IntervalYear
type Plan struct{ ID string; Price Money; Interval Interval; Currency string }
type Catalog map[string]Plan                      // key == Plan.ID

type EventType string                             // EventSubscribe (пока)
type Event struct{ At time.Time; Type EventType; PlanID string }

type Period struct{ Start, End time.Time }        // [Start, End)
func (p Period) Days() int
func (p Period) Contains(t time.Time) bool
func AddInterval(t time.Time, iv Interval) (time.Time, error)

type RuleID string
type Line struct{ RuleID RuleID; Description string; Amount Money }
type Invoice struct{ Currency string; Lines []Line; Total Money }

func Compute(c Catalog, events []Event, period Period) (Invoice, error)
```

Известное ограничение (осознанное): `Allocate` считает в int64 без big.Int — переполнение возможно при суммах ~10^14 центов с весами ~10^4; для домена подписок это за пределами реальности, отмечено в godoc.
