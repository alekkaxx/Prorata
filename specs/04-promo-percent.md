# 04-promo-percent — процентный промокод (одноразовый)

Тир спеки: architect. Реализация: builder (`rule_promo.go`). Фикстуры/тесты: mechanic.

Ядро для этого правила уже подготовлено architect'ом (коммит
`core(promo): EventApplyPromo, отложенная скидка в state, хук applyPromo`),
по образцу подготовки кредитного баланса в правиле 03:

- `EventApplyPromo` и поля `Event.Bps` (базисные пункты) / `Event.Code`
  (код промо);
- `state.promo` (`pendingPromo{armed, bps, code}`) — отложенная одноразовая
  скидка;
- хук `applyPromo` в `engine.go` между правилом и `applyCredit` — применяет
  скидку к положительным зарядам события и сжигает промо; RuleID строки —
  `promo.percent`;
- `formatPercent(bps)` — рендер процента для описания строки.

Builder пишет **только** `rule_promo.go` — правило-обработчик `EventApplyPromo`,
которое валидирует и **взводит** `state.promo`. Само применение скидки и строку
`promo.percent` делает ядро (`applyPromo`), правило её не создаёт. Ядро не трогать.

## Что делает правило

Процентный промокод — одноразовая скидка N% на **следующее списание**. Механика
разнесена на две фазы:

**Фаза 1 — взведение (правило `rule_promo.go`, событие `EventApplyPromo`):**

1. Код обязателен: если `ev.Code == ""` → ошибка `prorata: promo: empty code`.
2. Диапазон bps: если `ev.Bps < 0 || ev.Bps > 10000` → ошибка
   `prorata: promo: bps <n> out of range [0,10000]` (`<n>` = `ev.Bps`).
3. Одноразовость на взведении: если промо уже взведён и ещё не сгорел
   (`st.promo.armed`) → ошибка `prorata: promo: promo already pending`.
4. Иначе `st.promo = pendingPromo{armed: true, bps: ev.Bps, code: ev.Code}`.
5. Правило **не возвращает строк** (`nil, nil`). Активная подписка НЕ требуется
   (см. D5).

**Фаза 2 — применение (ядро `applyPromo`, для каждого события после его правила):**

1. Если промо не взведён (`!st.promo.armed`) — ничего не делает.
2. `base` = сумма **положительных** `Amount` строк события (валовой заряд).
   Отрицательные строки (например `prorate.credit`) в базу не входят.
3. Если `base <= 0` — ничего не делает, промо **остаётся взведён** (ждёт первого
   реального заряда).
4. Иначе: `discount = base.Percent(bps)` (округление half away from zero, D1
   ядра); добавляется одна строка `promo.percent` с `Amount = -discount`; промо
   **сжигается** (`st.promo = pendingPromo{}`).

`applyPromo` выполняется **до** `applyCredit`, поэтому кредитный баланс гасит уже
удешевлённый чистый заряд (D2).

Напоминание из ядра: `applyPromo` (как и `applyCredit`) отрабатывает и для
событий вне запрошенного периода — чтобы леджер промо был согласован через
границу периода; строка `promo.percent` попадает в инвойс только для событий
внутри периода.

## Ключевые решения (решение → почему → отвергнутая альтернатива)

### D1. Модель — отдельное событие `EventApplyPromo`, скидка живёт в state до следующего заряда

**Решение:** промо — самостоятельное событие `EventApplyPromo` с процентом в
базисных пунктах (`Event.Bps`) и кодом (`Event.Code`). Оно не заряжает ничего
само, а **взводит** одноразовую скидку в `state.promo`. Первое последующее
событие, породившее положительный заряд (subscribe / upgrade / downgrade), эту
скидку потребляет.

**Почему:** у промо нет собственной суммы заряда — оно всегда «скидка на будущее
списание». Отложенная скидка в state держит свёртку `[]Event` детерминированной и
позволяет удешевить заряд **любого** правила единым движковым хуком, не редактируя
`rule_charge`/`rule_prorate`/`rule_downgrade` (симметрия с `applyCredit` правила
03). Промо-до-subscribe (акция «первый месяц −20%») ложится в модель бесплатно.

**Отвергнуто:** промо как поле заряжающего события (`Upgrade` несёт `Bps`) —
привязывает скидку к одному правилу, не даёт удешевить обычный `subscribe`,
заставляет каждое правило-заряд повторять логику скидки; промо, применяемое
«внутри своего же события» — невозможно, событие промо заряда не порождает.

### D2. Порядок — скидка ДО кредитного баланса; только на положительные заряды

**Решение:** хук `applyPromo` стоит между правилом и `applyCredit`. База скидки —
сумма только **положительных** строк события; отрицательные (кредит остатка
апгрейда) не удешевляются. Кредитный баланс (`credit.applied`) затем считается по
**чистому заряду с уже вычтенной скидкой**.

**Почему:** скидка — это «−N% от того, что с тебя списывают», а не от возврата;
удешевлять refund бессмысленно. Применяя баланс к **удешевлённому** нетто, мы не
даём предоплате клиента сгорать против той части заряда, которую и так покрыла бы
скидка. Порядок строк события: `[…заряды/кредиты правила…, promo.percent,
credit.applied]`. Пример 3 доказывает важность порядка: `credit.applied` там
считается по 1000 (после скидки), а не по 2000 — иначе итог ушёл бы в −1000
(фантомный refund).

**Отвергнуто:** скидка ПОСЛЕ баланса (`credit.applied` по валовому заряду, потом
скидка) — предоплата гасит заряд, который покрыла бы скидка, баланс
переиспользуется экономически неверно, итог может уйти в минус; скидка на все
строки, включая кредитные — урезает возврат клиенту, рвёт интуицию «кредит ≤
уплаченного».

### D3. Одноразовость — промо сгорает при первом реальном срабатывании

**Решение:** `state.promo` хранит взведённую скидку. `applyPromo` сжигает её
(`st.promo = pendingPromo{}`) **в момент, когда действительно выпустил строку
`promo.percent`** (т.е. когда `base > 0`). Если очередное событие не дало
положительного заряда (`base <= 0`), промо остаётся взведён и ждёт первого заряда.

**Почему:** «одноразовый» из бэклога. Сжигание по факту скидки (а не по факту
«следующего любого события») устойчиво к no-op-событиям: промо, взведённый перед
событием без заряда, не испаряется молча.

**Отвергнуто:** сжигать на непосредственно следующем событии независимо от
заряда — промо, взведённый перед событием без положительного заряда, пропал бы
впустую.

### D4. Округление — half away from zero через `Money.Percent`

**Решение:** `discount = base.Percent(bps)` — переиспользуется существующий
`Money.Percent` (D1 ядра, half away from zero). Процент передаётся в базисных
пунктах (`bps`, 10000 = 100%), float в API нет.

**Почему:** единая стратегия округления по всему движку (D1 ядра); новой
арифметики скидка не вводит. `Percent` уже покрыт property-тестом
`TestPercentProperty` (знаковая симметрия, `|скидка| ≤ |база|`), поэтому скидка не
может превысить заряд и увести одиночный заряд в минус.

**Отвергнуто:** банковское округление half-even (противоречит D1 ядра);
усечение вниз (систематически в пользу одной стороны, необъяснимо клиенту).

### D5. Промо без активной подписки — отложенная скидка, не ошибка

**Решение:** `EventApplyPromo` НЕ требует активной подписки. Промо, взведённый до
`subscribe`, применяется к первому заряду — то есть к самому `subscribe` (акция
«первый период со скидкой»). Пример 2.

**Почему:** промо ортогонален состоянию подписки; «welcome»-скидка естественно
предшествует подписке. Взведение не нуждается в плане, а применение —
самодостаточный движковый хук над любыми положительными строками.

**Отвергнуто:** ошибка `no active subscription` на взведении — запретила бы самый
частый сценарий «первый месяц −20%» и внесла бы асимметрию в модель.

### D6. Повторное промо поверх несгоревшего — ошибка

**Решение:** взвести второй `EventApplyPromo`, пока предыдущий взведён и не сгорел
(`st.promo.armed`), → ошибка `prorata: promo: promo already pending`.
Последовательные промо, каждый из которых успел сгореть до следующего, легальны:
«одноразовый» означает «применяется один раз», а не «за всю историю один».

**Почему:** молчаливое наложение/замена прячут намерение вызывающего;
одноразовые скидки не должны копиться в очередь. Явная ошибка держит инвариант
«одна скидка на один заряд» без стекования — а стекование/запрет-стекования это
предмет правила №6 (фиксированный промокод), не этого.

**Отвергнуто:** замена (последний побеждает) — молча теряет первый промо;
суммирование/композиция двух промо — это стекование (правило №6), вне скоупа,
плюс порядок компаундирования становится неоднозначным.

## Инвариант «деньги не создаются, кредит ≤ уплаченного» при промо

- `promo.percent` всегда `≤ 0` и по модулю `≤ base` (`Money.Percent` ограничен
  модулем базы). Значит скидка не может превратить одиночный положительный заряд
  в отрицательный — промо сам по себе не порождает refund.
- Скидка не трогает `creditBalance`. `applyCredit` по-прежнему берёт
  `applied = min(net, balance)`, только `net` теперь **меньше** (удешевлён). То
  есть `credit.applied` после промо не больше, чем был бы без него — инвариант
  «кредит ≤ уплаченного» лишь усиливается.
- `Total = Σ строк` считает ядро; скидка — обычная строка, деньги не теряются.

## RuleID и формат строк

| строка | RuleID | Description | Amount | источник |
|---|---|---|---|---|
| применение скидки | `promo.percent` | `<code>: -<pct>% off <base>` | `-discount` (≤ 0) | ядро (`applyPromo`) |

- `<code>` — `ev.Code` как есть (не трансформируется).
- `<pct>` — `formatPercent(bps)`: целый процент без дроби, если `bps % 100 == 0`
  (`fmt.Sprintf("%d", bps/100)`), иначе две десятичные (`fmt.Sprintf("%d.%02d",
  bps/100, bps%100)`). Примеры: `2000 → "20"`, `750 → "7.50"`, `10000 → "100"`,
  `0 → "0"`.
- `<base>` — валовой положительный заряд события через `Money.String`
  (`"480.00"`, `"20.00"`).
- Правило `rule_promo.go` строк не порождает (`nil, nil`).

## Краевые кейсы

- **Промо без активной подписки** (D5): взводится, применяется к первому заряду
  (в т.ч. к самому `subscribe`). Пример 2.
- **Повторное промо поверх несгоревшего** (D6): ошибка
  `prorata: promo: promo already pending`.
- **Пустой код**: ошибка `prorata: promo: empty code`.
- **bps вне диапазона** (`<0` или `>10000`): ошибка
  `prorata: promo: bps <n> out of range [0,10000]`.
- **Промо 0%** (`bps == 0`): при `base > 0` выпускается строка `promo.percent`
  с `Amount = 0` (нулевая строка легитимна и объяснима, как нулевой
  `prorate.credit` в правиле 02); промо сгорает.
- **Промо 100%** (`bps == 10000`): скидка равна валовому заряду, чистый заряд
  события до баланса — ноль. Пример 4.
- **Промо + апгрейд в одном инвойсе**: скидка считается по валовому заряду
  (`prorate.charge`), кредит остатка (`prorate.credit`) не удешевляется; порядок
  строк `[prorate.credit, prorate.charge, promo.percent]`. Пример 1.
- **Промо + даунгрейд + кредитный баланс**: скидка ДО `credit.applied`, баланс
  гасит удешевлённый нетто. Пример 3.
- **Событие-потребитель вне запрошенного периода**: промо всё равно сгорает
  (леджер согласован), строка `promo.percent` в инвойс не попадает.
- **Промо взведён, но следующее событие без положительного заряда**: промо не
  сгорает, ждёт первого заряда (D3).

## Примеры вход→выход (точные значения — фикстуры строить байт-в-байт)

### Пример 1 (витрина PLAN §2 — Pro→Business с промо −20%) → golden/04-promo-showcase.json

Юзер на pro-month с 1 января, 13-го апгрейдится на business-year, применив
одноразовый промо `WELCOME20` (−20%) перед апгрейдом. Промо удешевляет
**заряд нового плана**, кредит остатка старого не трогает.

Пересчёт честно по D1 правила 02: старый период `[2026-01-01, 2026-02-01)` =
**31** день; остаток `[2026-01-13, 2026-02-01)` = **19** дней, `used = 12`;
`2000.Allocate([12, 19]) = [774, 1226]` → кредит **1226**. Скидка:
`base = 48000`, `48000.Percent(2000) = 9600` → `promo.percent = −9600`
(`WELCOME20: -20% off 480.00`). Итог: `−1226 + 48000 − 9600 = 37174` ($371.74).
Кредитного баланса нет (даунгрейда не было) → `credit.applied` нет.

Запрошенный период начинается с даты апгрейда; subscribe (1 января) в него не
входит, `apply_promo` строк не даёт.

Вход:
```json
{
  "name": "04-promo-showcase",
  "catalog": [
    {"id": "pro-month", "price_cents": 2000, "interval": "month", "currency": "USD"},
    {"id": "business-year", "price_cents": 48000, "interval": "year", "currency": "USD"}
  ],
  "events": [
    {"at": "2026-01-01T00:00:00Z", "type": "subscribe", "plan": "pro-month"},
    {"at": "2026-01-13T00:00:00Z", "type": "apply_promo", "bps": 2000, "code": "WELCOME20"},
    {"at": "2026-01-13T00:00:00Z", "type": "upgrade", "plan": "business-year"}
  ],
  "period": {"start": "2026-01-13T00:00:00Z", "end": "2027-01-13T00:00:00Z"}
}
```

Выход:
```json
{
  "currency": "USD",
  "lines": [
    {"rule": "prorate.credit", "description": "pro-month: unused 19/31 days 2026-01-13 to 2026-02-01", "amount_cents": -1226},
    {"rule": "prorate.charge", "description": "business-year: full period 2026-01-13 to 2027-01-13", "amount_cents": 48000},
    {"rule": "promo.percent", "description": "WELCOME20: -20% off 480.00", "amount_cents": -9600}
```

### Пример 3 (промо + даунгрейд — скидка ДО кредитного баланса) → golden/04-promo-downgrade-order.json

Subscribe team-month 1 января, `apply_promo HALF` (−50%) и downgrade на pro-month
13 января. Даунгрейд банкует остаток team: старый период
`[2026-01-01, 2026-02-01)` = **31** день, остаток **19** дней, `used = 12`;
`5000.Allocate([12, 19]) = [1935, 3065]` → банкуется **3065**. Заряд pro-month
`+2000`, период `[2026-01-13, 2026-02-13)`.

Порядок применения (ядро): сначала скидка — `base = 2000`,
`2000.Percent(5000) = 1000` → `promo.percent = −1000` (`HALF: -50% off 20.00`);
затем баланс по **удешевлённому** нетто `net = 2000 − 1000 = 1000`,
`applied = min(1000, 3065) = 1000` → `credit.applied = −1000`. Итог
`2000 − 1000 − 1000 = 0`; на балансе остаётся **2065** (в инвойсе не виден).

Если бы баланс шёл ДО скидки, `credit.applied` было бы −2000, а итог −1000
(фантомный refund) — этот кейс фиксирует правильный порядок.

Запрошенный период — с даты даунгрейда; subscribe (1 января) в него не входит.
