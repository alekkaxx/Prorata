# prorata — биллинг-движок как витрина AI-конвейера

> Репо: `~/go/src/arnur-interview-task`, Go-пакет и рабочее имя движка — `prorata`.
> **Этот файл — единственный источник контекста.** Новая сессия читает его ПЕРВЫМ и целиком.
> Придуман 2026-07-23 в сессии с Fable 5 (обсуждение шло от «маленький кусок кода, показывающий уровень» → «умный CLAUDE.md с модельным роутингом» → «нужна настоящая логика, не ката»).

---

## 1. Зачем этот проект существует (мета-цель — она ГЛАВНАЯ)

Проект — **публичная визитка того, как автор обращается с AI при разработке**. Не скрываем, что код ИИшный — наоборот, это и презентуем. Две вещи, которые должен увидеть зритель (техлид/работодатель), потратив 10 минут:

1. **Настоящая доменная логика в маленьком объёме.** Не CRUD и не учебная ката (интерпретаторы/LRU отклонены именно за это): биллинг — область, где куча краевых случаев, решения принимаются, а не вспоминаются, и неправильный ответ стоит денег. Любой, кто трогал биллинг, опознаёт глубину с одного сценария.
2. **Образцовый CLAUDE.md-«станок»:** маршрутизация задач по моделям в зависимости от сложности (дешёвая модель — механика, средняя — типовые правила, дорогая — архитектура и гейты), правила эскалации, токен-экономия, машинная верификация, оправдывающая доверие дешёвым моделям. CLAUDE.md рулит НЕ продуктом (продукт Claude API не зовёт вообще), а **процессом написания кода**.

Ключевой принцип витрины: **каждое правило CLAUDE.md обязано иметь видимый след в репо.** Написано «gate обязателен» — в репо есть `make check` и golden/. Написано «правила пишет builder» — в истории коммитов это видно. CLAUDE.md, проверяемый глазами за 5 минут, — вот определение «по красоте».

Эталон жанра, от которого отталкиваемся: CLAUDE.md проекта CaloBro (`~/go/src/calories bot/CLAUDE.md`) — но там тиринг моделей внутри продукта, а здесь тиринг в процессе разработки. Это принципиальная разница.

## 2. Что за продукт

**Go-библиотека, отвечающая на один вопрос: «сколько списать?».**

Вход: план подписки, история событий подписки (старт, апгрейд, даунгрейд, отмена, промокод), запрошенный период. Выход: `Invoice` — строки списаний/кредитов с объяснением каждой строки и итогом.

Примерный сценарий-витрина (он же пойдёт в README):

> Юзер с месячным тарифом Pro ($20/мес) 13-го числа апгрейдится на годовой Business ($480/год) с промокодом −20% на первый период. Что в счёте?
> Движок: кредит за неиспользованные 17/30 Pro (+$11.33), списание года Business со скидкой (−$384.00), итог −$372.67, каждая строка со ссылкой на правило, которое её породило.

**Жёсткие границы скоупа (не расширять — это витрина, не продукт):**
- Библиотека. НЕТ HTTP, НЕТ БД, НЕТ CLI, НЕТ Stripe-интеграций. Чистые функции: события на входе → инвойс на выходе.
- НЕТ конкурентности — движок однопоточный по своей природе, не изобретать.
- Одна валюта на подписку (мультивалютность — из скоупа).
- Продукт не использует LLM. Весь AI — в процессе разработки.

## 3. Ядро домена (проектирует ДОРОГАЯ модель, сессия-1)

Опорные решения, которые надо принять в дизайн-сессии (не предрешаю, но фиксирую вопросы):

- **Money**: минорные единицы (int64 центы), никакого float. Явная стратегия округления (half-even vs half-up?) и — важнейший инвариант — **распределение суммы по частям без потери копейки** (largest remainder method: остаток от деления достаётся по правилу, сумма частей ВСЕГДА равна исходной).
- **Period / Proration**: считать по дням или по секундам? Месяц = календарный или 30 дней? Это ДОРОГИЕ решения — у каждого варианта есть последствия в краевых кейсах (31-е число, февраль, високосный год).
- **Событийная модель**: `[]Event` (Subscribe, Upgrade, Downgrade, ApplyPromo, Cancel, Refund) → расчёт детерминирован и идемпотентен. Пересчёт того же входа даёт тот же инвойс байт-в-байт (это свойство — в property-тесты).
- **Объяснимость**: каждая строка инвойса несёт `RuleID` и человекочитаемое «почему». Инвойс, который не может объясниться, — баг по определению.
- **Инварианты** (фундамент доверия дешёвым моделям): деньги не создаются и не исчезают; кредит ≤ уплаченного; идемпотентность; сумма allocation = исходной сумме.

## 4. Матрица задач → модельный роутинг (сердце витрины)

| Класс задачи | Модель/агент | Верификация (почему модели можно доверять) |
|---|---|---|
| Дизайн ядра (Money, Period, событийная модель, публичный API), спорные решения округления, разбор упавших property-тестов | **architect** (Opus/Fable) | ревью человеком, дизайн-запись в specs/ |
| Реализация одного правила биллинга по готовой спеке, его стандартные тесты | **builder** (Sonnet) | спека + golden-сценарии + property-тесты + гейт architect |
| Табличные тест-кейсы по спеке, golden-фикстуры, механические правки по образцу, доки | **mechanic** (Haiku) | компилятор + `make check` — человек не нужен |

**Эскалация вверх (обязательная):** 2 проваленные попытки пройти гейт подряд → задача уходит на тир выше. Задача трогает публичный API или инварианты → только architect. Property-тест упал → разбирает architect (это сигнал о дыре в дизайне, не в правиле).

**Запрет спускаться вниз:** mechanic не начинает без спеки и фикстур; builder не начинает без спеки в `specs/`.

**Токен-экономия:** новая сессия читает этот PLAN и головы спеки текущей задачи — НЕ весь репо; golden-файлы не читать целиком (только упавшие диффы); разведку по коду — узким сабагентом, в основной контекст только вывод.

**След экономики:** в README вести табличку «правило → тир, которым доехало → число заходов». Именно она докажет, что роутер не декорация.

## 5. Структура репо (целевая)

```
arnur-interview-task/          # пакет prorata
├── CLAUDE.md                  # витрина — черновик в §8, дошлифовать в сессии-1
├── PLAN.md                    # этот файл
├── README.md                  # сценарий-витрина + «как это написано» + экономика
├── .claude/
│   ├── agents/
│   │   ├── architect.md       # model: opus (или inherit при работе из Fable-сессии)
│   │   ├── builder.md         # model: sonnet
│   │   └── mechanic.md        # model: haiku
│   └── skills/
│       └── add-rule/SKILL.md  # ритуал «добавить правило биллинга» (конвейер §6)
├── specs/                     # NN-<rule>.md — спека каждого правила ДО кода
├── golden/                    # NN-<scenario>.json — вход-события + эталонный инвойс
├── money.go period.go plan.go event.go invoice.go engine.go   # ядро
├── rule_charge.go rule_prorate.go rule_promo.go ...   # по правилу на файл
├── *_test.go + property_test.go                       # pgregory.net/rapid для property
└── Makefile                   # check = build + vet + test (+ golden)
```

Конвенция: **одно правило = один `rule_*.go` + одна спека + свои golden.** Прямой аналог vertical slice.

Стиль кода: **все комментарии в `.go`-файлах — godoc-стиль, на английском.** Русский язык живёт только в PLAN/README/спеках/коммитах.

## 6. Конвейер добавления правила (ритуал, он же скилл add-rule)

1. **architect**: спека в `specs/NN-<rule>.md` — что делает правило, краевые кейсы, 3–5 примеров вход→выход цифрами.
2. **mechanic**: по спеке — golden-фикстуры и табличные тесты (падающие).
3. **builder**: реализация `rule_*.go`, пока `make check` не зелёный.
4. **architect**: гейт — ревью диффа против спеки и инвариантов; вердикт в спеку (`## Gate: pass/fail + причина`).
5. Строка в README-табличку экономики.

## 7. Бэклог правил (порядок обкатывает все тиры уже к третьему пункту)

1. **Ядро** (architect): Money + allocation-инвариант, Period, Event, Invoice, engine-каркас. Первые property-тесты.
2. **Полное списание периода** (builder — простейшее правило, обкатка конвейера end-to-end).
3. **Proration при апгрейде** посреди периода: кредит остатка + списание нового (первое настоящее мясо).
4. **Даунгрейд** — кредит на будущее, не refund (решение: кредитный баланс).
5. **Промокод процентный** — одноразовый, порядок применения относительно proration.
6. **Промокод фиксированный** — и запрет стекования (первый конфликт правил).
7. **Годовой ↔ месячный** переходы в обе стороны (проверка Period-решений на прочность).
8. **Trial** и конверсия в платный.
9. **Refund-политики**: полный / пропорциональный / кредитом.
10. **VAT** поверх: округление по строкам vs по итогу (классическая ловушка — суммы расходятся на копейку).
11. **Grace period** при неоплате.
12. **Отчёт-экономика** в README + шлифовка CLAUDE.md по фактическому опыту.

## 8. Черновик CLAUDE.md (сессия-1 материализует и дошлифует)

```markdown
# prorata

Биллинг-движок подписок: события → инвойс с объяснением каждой строки.
Библиотека, чистые функции. НЕТ: HTTP, БД, CLI, конкурентности, LLM в рантайме.
Витрина AI-конвейера: этот файл маршрутизирует РАЗРАБОТКУ по моделям. Контекст проекта — PLAN.md.

## Роутинг задач по моделям

| Задача | Агент | Гейт |
|---|---|---|
| дизайн ядра/API, округления, упавшие property | architect (opus) | ревью человека |
| правило по спеке + тесты | builder (sonnet) | golden + property + architect |
| фикстуры, табличные тесты, механика, доки | mechanic (haiku) | make check |

Эскалация: 2 фейла гейта подряд → тир выше. Публичный API или инварианты → только architect.
Вниз: без спеки в specs/ builder и mechanic не стартуют.

## Инварианты (нарушение = стоп и architect, не «подкрутить тест»)

- Деньги не создаются и не исчезают: сумма allocation == исходной сумме.
- Расчёт идемпотентен: тот же вход → байт-в-байт тот же инвойс.
- Кредит ≤ фактически уплаченного.
- Каждая строка инвойса несёт RuleID и объяснение.

## Конвейер правила

спека (architect) → фикстуры+падающие тесты (mechanic) → реализация (builder)
→ гейт (architect, вердикт в спеку) → строка в README-экономику.
Ритуал: skill add-rule.

## Структура

Одно правило = rule_<name>.go + specs/NN-<name>.md + golden/NN-*.json.
Ядро: money.go period.go event.go invoice.go engine.go — менять только через architect.

## Стиль кода

Все комментарии — godoc, на английском. Русских комментариев в .go-файлах не бывает.

## Без явной просьбы — НЕ делать

- Не создавать файлы вне конвенции (helpers.go/utils.go запрещены).
- Не менять ядро и публичный API в задачах уровня builder/mechanic.
- Не расширять скоуп (HTTP/БД/CLI/валюты) — витрина, не продукт.
- Не читать golden целиком — только диффы упавших.

## Проверка

make check = go build + go vet + go test ./... (property на pgregory.net/rapid).
Перед коммитом — зелёный make check, других условий нет.
```

## 9. План сессии-1 (пошагово)

1. Прочитать этот PLAN целиком. `git init`, первый коммит — PLAN.md.
2. Материализовать CLAUDE.md (из §8), `.claude/agents/` (3 файла с `model:` в frontmatter), скилл `add-rule`, Makefile.
3. **Дизайн-сессия ядра дорогой моделью** (бэклог №1): решить вопросы из §3, зафиксировать решения в `specs/00-core.md` (формат: решение → почему → отвергнутая альтернатива), реализовать ядро + property-тесты.
4. Прогнать правило №2 (полное списание) через конвейер §6 строго по ролям — даже если кажется избыточным: цель — обкатать и показать станок.
5. Начать README: сценарий-витрина + пустая табличка экономики.
6. Коммиты — по шагам конвейера, с указанием тира в теле коммита (след для зрителя).

## 10. Чего НЕ делать (уже отклонённые повороты — не переизобретать)

- Не превращать в продукт/SaaS — ценность в станке и глубине логики, не в фичах.
- Не добавлять LLM в рантайм движка — тиринг моделей здесь про процесс разработки (это главное отличие от CaloBro, не «недоделка»).
- Не брать учебные каты (интерпретатор, LRU, worker pool) — отклонено: «несложно = нерепрезентативно».
- Не писать тонну кода дорогой моделью — это ломает саму идею витрины.
